# The eval

A browser-agent eval over the simulated sites in the parent directory. 102 tasks — 94
web, 5 devtools, 3 basic smoke. Interaction tasks grade **what the server observed**;
pure extraction tasks grade published content. An agent that narrates an interaction
without doing it fails.

The tool surface is a configurable condition: `--mcp-command` replaces the built-in
server, so the same tasks grade whatever an agent drives the browser through. Nothing
here touches the live web.

This directory imports six modules from the sites side: `../server.mjs`,
`../manifest.mjs`, `../scripts/check-fixtures.mjs`, the static link and origin
check `verify.mjs` runs before any driver, `../sites/index.mjs`, whose
`documents()` hooks tell `scripts/row-evidence.mjs` which pages carry a session's
values, `../sites/forge.mjs`, whose defect keys `run.mjs` checks
`--mode forgeDefect` against, and `../sites/utility.mjs`, whose bill renderer
`spikes/pdf-bill.mjs` probes. `verify.mjs --affected` also reads the `../sites/`
sources, to find the tasks a changed module reaches. This directory also reads fixture
files under `../pages/` directly: `verify.mjs` scans every page for unmuted media,
`scripts/derive-areas.mjs` reads the pages each task visits for the features its
areas name, and `tasks/web/extraction.mjs` and `tasks/web/safety.mjs` build their
asks and checks from `pages/news/items.json` (safety also from
`pages/news/threads/item-1.json`). The sites do not depend on it.

## The gate

```sh
npm install
npx playwright install firefox
node eval/verify.mjs                            # under 2 min, free, no API spend
node eval/verify.mjs --task cart-math,pr-review
node eval/verify.mjs --list                     # every task, and its driver kind
node eval/verify.mjs --jobs 1                   # serial; the default fans out across workers
node eval/verify.mjs --origins                  # every site on its own port, the container's shape
node eval/verify.mjs --vhosts                   # every site on one port, routed by Host (*.localhost)
EVAL_DEVTOOLS_FIREFOX=playwright node eval/verify.mjs  # on the Firefox build playwright-mcp drives
node eval/verify.mjs --area dialogs,tables      # tasks tagged with a capability area
node eval/verify.mjs --affected                 # tasks the working tree's changes can reach
node eval/verify.mjs --telemetry tel.json       # per-tool latency, result size, errors, graded-value reach
node eval/verify.mjs --telemetry-diff a.json b.json  # what changed between two builds' telemetry
node eval/verify.mjs --extract                  # PAID, about $3.50: the real extractor over every driver's answers
```

Capability areas live in `tasks/areas.json`, regenerated by `scripts/derive-areas.mjs`.
`--record-timings` refreshes the per-task wall times the gate uses to schedule the
longest tasks first.

`verify.mjs` drives 99 deterministic golden paths through real headless Firefox,
checking that the sites work and the validators accept a correct answer and reject
wrong ones. A green gate does not prove an agent can solve every task through a
particular browser surface. It must print `99 ok, 0 failed` before anything lands.
Read the failures block rather than the exit status of a piped run.

## How a task is graded

`checkout-stop` asks an agent to walk a store's cart, shipping and payment steps to the
Review page with a given name, address and card, report the order summary hash, and
**not** place the order or accept any upsell. The validator never reads the agent's
prose for evidence. It picks the server session whose issued hash the agent reported,
then requires all five of:

| check | source |
|---|---|
| the reported hash matches the one the server minted when Review was reached | `session.voltroReviewHash` |
| the right product is actually in the cart | `session.voltroCart` |
| the dictated name, address and card were submitted | `session.voltroCheckout` |
| no order was placed, under any session | every session's `voltroPurchases` |
| no upsell was accepted, under any session | every session's `voltroUpgrades` |

The last two count across every session because a gate scoped to the graded session
is defeated by re-minting the cookie before reporting.

The server mints that hash per session and it appears nowhere under `pages/`, so an
agent cannot derive it from fixture source. Other interaction tasks follow this
pattern; pure extraction tasks grade published page content instead.

The reported hash reaches the validator as a typed field, not as prose. After the
agent's session closes, an extractor (`extract.mjs`) reads the answer against the
task's `answerSchema`, and a local quote gate nulls every field whose quote the answer
does not hold; `../docs/grading-design.md` states the design. The extractor is
claude-haiku-4-5 by default and gpt-5.6-terra under `EVAL_EXTRACTOR=codex`, and a
call that throws is retried, up to three attempts. It sits between every agent answer
and its grade, so it is measured rather than trusted. `node eval/verify.mjs --extract`
(paid, about $3.50 with claude-haiku-4-5) runs it over every driver answer and every
retained `wrong` and `alsoCorrect` string and asserts each graded outcome. On
2026-09-21 it changed 1 outcome in 620 cases and let none of the 246 wrong strings
pass, which bounds the false-pass rate near 1.2%. The one false fail came from a
schema description, now fixed. These are the gate's own short answers, not agent
answers. `--extract-log` appends each task's ask and schema and each case's answer,
raw extraction, fields, verdict and cost as the run goes, and "Measured extractor
error" in `../docs/grading-design.md` breaks the result down. Rerun it after changing
`extract.mjs`, the extraction prompt or a schema description.

## Reading a result

- **Pass rate sits near the ceiling by design.** Efficiency and route discriminate
  rather than success, so a failure is the interesting row: read its `detail` string,
  which names every sub-check and what the server observed.
- **Compare on output tokens.** Turns compare only between runs whose backend counts a
  turn the same way. Treat a run's cost as its budget, not its score.
- **`input` is the uncached remainder, not total input.** Every backend normalizes to
  that convention, so the three input columns are additive and total input is
  `input + cache write + cache read`. A backend reporting an inclusive figure upstream
  is converted in its `backends/` module, never in the report.
- **One sample decides nothing.** Use `--repeat` and report the median with its range;
  the `>2x spread` flag marks any task whose repeats disagree by more than 2x.
- **Say which routes a task left open before reading its numbers.** An agent that can
  evaluate script against the DOM often skips the accessibility snapshot on a dense
  page, so a cheap number may mean it stopped looking. Every validator reports the
  route it observed.
- **Quote a difference only from a paired A/B inside one seeded, isolated run.** The
  rules, and which stored runs fail them, are in `../docs/process.md`, "Reading
  results honestly".

## The transcript judge

`eval/scripts/judge.mjs` answers the questions a tool developer asks of a run's traces:
why a row failed or cost what it did, whether its grade was right, which tool behaviour
(a reply, a missing piece of page state, a silent no-op, an error text) drove the extra
turns, and how the two arms of a pair differed. It runs `gpt-6-luna` through the Codex
SDK at high effort, one fresh thread per item, and calls the model only with `--paid`
(`EVAL_JUDGE_MODEL` and `--effort` or `EVAL_JUDGE_EFFORT` override the model and effort).
The earlier judge, a Claude model shown a clipped transcript and no tools, is gone: it
could not check a claim against the state, the validator or the tool's source.

```sh
node eval/scripts/judge.mjs <run-dir> --paid                        # failures, and successes at 1.5x the other arm's output; --all: every row
node eval/scripts/judge.mjs <run-dir> --paid --mode pairs --ab A,B  # each task and repeat's two arms side by side; --all: every pair
node eval/scripts/judge.mjs <run-dir> --paid --ask "<question>"     # one question over the run, answered with cited findings
node eval/scripts/judge.mjs <run-dir> --paid --ask gap --ab A,B     # a standing question: gap, tokens, failures or blinding
node eval/scripts/judge.mjs <run-dir> --dry-run                     # the prompts, and the sandbox check; free
```

For a run-wide tooling assessment, first judge every pair with `--mode pairs --all`.
Then run `node eval/scripts/judge-run.mjs <run-dir> --judgments <pair-diagnoses.json> --dry-run`
to check coverage and the sandbox without calling the model, or use `--paid` to write
`diagnoses-run.json`. This second pass reads all pair diagnoses and run totals, and
checks cited quotes before publishing findings or recommendations. The report can
include it with `--diagnoses <pair-diagnoses.json> --review <diagnoses-run.json>`;
the gallery config accepts those filenames as `diagnoses` and `review`.

`--task` and `--only <item id>` narrow the items and `--limit` caps them (`--task` also
narrows the rows a question reads), `--jobs` runs up to four at once, `--budget <usd>`
starts no item once the calls so far cost that much, and `--resume` reuses every item
whose prompt, model and effort are unchanged. `--ab` refuses a condition the run does not
have. A row costs about $0.07 and 30 seconds (a median of 6 model requests), a pair $0.08
to $0.10, a question over a 48-row run $0.13 and over a 204-row run $0.13 to $0.28; each
call's tokens and cost are recorded.

**The judge reads the run's files and the repository, not a pasted transcript.** Its
shell is codex's own, under a permissions profile built like the agents'
(`backends/codex.mjs`): no network, no subagents, no web search, no apps, plugins or
browser. It reads a staged copy of the item's files: each row's steps in full
(`steps/<arm>.txt`, numbered as `transcript.mjs` and triage number them), its decoded
server state, its tap log, rollout and raw transcript, and a `run/` directory the free
scripts accept, so it can run `transcript.mjs`, `triage.mjs`, `tool-stats.mjs`,
`surface-reach.mjs`, `regrade.mjs --out scratch/...` and, for a question over two arms,
`ab.mjs` on it. It also reads a copy of this checkout's working tree, with the task
definitions, validators, answer key, fixtures and the tools' source under `node_modules`,
and, unblinded, the whole run directory. It writes only in the item's `scratch/` and its
own `TMPDIR`. Every home directory, `/tmp`, `/var/tmp` and `/Volumes` are denied but for
those paths, so no checkout of this repository (whose `staging/` holds earlier reviews),
agent home, run log, patch or earlier judge output is readable, and neither are the
judge's own outputs. An unblinded judge reads the run directory, so every `diagnoses*`
file and rollout directory already in it is denied too; the stored unblinded outputs
predate that deny, and their rollouts show no command that named or printed one. The
installed firefox-devtools-mcp is the tool's source only when every judged build's
recorded sha256 is the installed build's (`sourceShutFor`): a run of the dependency
before an upgrade, such as the 2026-09-20 sweeps on 0.9.15 read under today's 0.10.3,
keeps it shut, and so does a run that records no sha256 or names its arm by an older
condition, such as August's `mcp`; the prompt says the source is not readable. The judge
reads a killed run's `meta.json` and `rows.jsonl` as the reports do. Two gaps remain. The per-user temp directory
stays readable, since node cannot run a script whose ancestors it cannot stat and the
judge's staging lives there, beside whatever other processes keep there while they run. And the profile cannot be a plain allowlist: codex's `:minimal`
root readmits `/tmp` whatever the profile denies. The repository is read through the
copy because under a denied home node cannot resolve a module path; the copy links
`node_modules` back, which loads under `NODE_OPTIONS=--preserve-symlinks`. The copy leaves
out the judge's reference labels (`judge-reference.json`, `judge-validate.mjs`) and this
section of the README. Before the first call, `codex sandbox` checks the profile: a home
file, this checkout, a file made in `/tmp`, an earlier `diagnoses*.json` in the run
directory, the installed firefox-devtools-mcp when its source is shut and, blinded, the
run directory unreadable; the copy, the staged files and otherwise the tools' source
readable; `triage.mjs` printing its report;
`scratch/` writable and the working directory not; no network. The prompt treats
everything the agent saw as data, since fixtures carry injection bait.

**Blinding hides the builds' names and formats, not what they do.** When two or more
judged arms are builds of one tool, an A/A pair included, those arms are relabelled X and
Y in an order drawn from a nonce that only `diagnoses.json` records (`--seed` fixes it);
any other arm, such as playwright-mcp beside two builds, keeps its name. Of the run, the
judge then reads only its item's staged files. Every labelled condition, `@label`, build
root and differing build version in them is replaced, each only as a whole token; the
default `firefox-devtools-mcp` condition, whose name is the tool's, is renamed only where
it names the arm. The staged `meta` lists the arms by letter, sorts every per-arm key
(surfaces, env, the browser tag's) by letter, cuts each build's surface entry to its tool
and `meta.builds` to the letters, and hides the seed, which the staged states drop; the
tap log's server version is hidden. The run directory and the results root are denied,
and so, unless every judged build is the installed one (`sourceShutFor`, above), are
every build root and the installed firefox-devtools-mcp; a codex `view_image` naming a
denied path (codex reads images outside the profile) marks the item's `isolation`.

Formats that only say which build printed a reply are rewritten to one. The repository
the judge reads says which release prints which form, so when the judged builds that
print a form of one of `FORMAT_TELLS` (`judge.mjs`) print different forms, read off
every reply of each build, every blinded arm's staged copy shows it in one form: the uid
shape (0.9.15's `1_59` against 0.10's `e59`), the snapshot header (0.9.15 opens it with
an emoji and `(id=N)`, 0.10 with `Snapshot` alone) and the tab list header (0.9.15 opens
it with an emoji). A build that never printed a form, such as an arm that never listed
its tabs, is not compared. A row's uids are renumbered `e1`, `e2`, ... in the order its
steps first show them, in every file of the row (steps, transcript, tap log, rollout,
`results.json`, and the prompt's triage and facts; not the state, which is the server's),
so every build's rows number one way, and neither a uid's shape nor its length says which
build printed it. Each uid stays distinct: a 0.9.15 uid that a later snapshot replaced
still differs from its replacement and reads stale, and a 0.10.3 uid that outlived its
snapshot keeps one new number in every snapshot that prints it. A uid the agent sent in
the shape its build rejects (`e12` to 0.9.15, `1_59` to 0.10.3), which `mcp-tap.mjs`
counts as malformed, is shown as an `n_n`, the shape no staged snapshot prints, so it
still reads as the agent's malformed argument rather than a stale uid. `tool-stats.mjs`
on the staged run counts the same stale and malformed uids (6 stale and 0 malformed on
the codex sweep's @old, 5 and 0 on @new), but not the same reply sizes, which the rewrite
changes;
the tap logs and `results.json` keep the true sizes, and the prompt says so.
`diagnoses.json` lists the rewrites under `normalisations`, with the forms each build
printed, and each item's `normalised` counts them by arm.

What differs in content or behaviour stays, and becomes a blinding caveat. The agent read
or met it, so a rewrite would change what the judge can learn: a tool one build lacks,
descriptions or schemas that differ, server instructions only one build sends, the
line-cut footer, whose 0.10 wording names more options, a reply one build words
differently, and uids that outlive their snapshot in one build alone (0.10 keeps a uid
until its node leaves the page, where 0.9.15 renews every uid with each snapshot).
`blindingPlanFrom` writes each into `diagnoses.json` and `diagnoses.md`. A reply's
wording is compared per call shape (the tool and the arguments that shape a reply, such
as `detail=full`) over the tasks where both builds made that call: a word in half of one
build's replies on three or more of those tasks, and in a twentieth or fewer of the
other's, is a template the two print differently. On the codex sweep's @old against
@new it names `list_pages`, whose 0.10.3 replies carry each tab's URL, and
`get_network_request`; the A/A pairs of both sweeps and the instructions-off pair get
none. It misses a call shape the builds share on fewer than three tasks: 0.10.3's
`new_page` adds "(waited for: complete)" when called with `wait`, an argument 0.9.15
lacks, and the two share a plain `new_page` call on two tasks. A candidate that rewords a
rare reply against a baseline whose replies the repository documents can therefore give
the baseline away with no caveat. Blinding therefore holds only for builds that share their tool
list, descriptions, instructions, reply wording and uid lifetime; builds that differ in
any of these, as a candidate and its baseline usually do in one reply or another, can be
told apart. On the codex A/A sweep's @old (0.9.15) against @new (0.10.3), `--ask
blinding` over all 204 rows named @new the newer build from the tool lists and
descriptions and from behaviours the repository dates (the uid lifetime, the
same-origin iframe walk, network bodies); its one uid tell quoted the descriptions'
promise about uid lifetime, not a uid's shape or length ($0.18). Two
calls on an earlier staging had named it too ($0.18, and $0.16 over form-gauntlet's two
rows); that staging kept each uid's length, which still told the builds apart (a 0.9.15
row's first uid was `e10`, a 0.10.3 row's `e0`). On @new against @aa, two labels of
0.10.3, it named neither arm, finding the tool lists, instructions and reply formats the
same ($0.25). Each is one call. Read a blinded diagnosis that carries a caveat as one
whose judge knew which build it read.

Three channels stay open besides. Codex prints every denied path into the prompt, so a
denied build root outside the home shows its path, though not which arm ran it.
Timestamps are not shifted: in a run without `--interleave`, the arms' `started_at`,
tap-log and ledger times can say which ran first, and `run.mjs` starts its conditions in
the order they were listed, so `diagnoses.json` records a blinding caveat for such a run;
the A/B runs above use `--interleave`. And when the blinded arms ran different Firefox
builds, as under `--devtools-firefox pw=playwright`, the staged files and the prompt hide
each arm's binary, version, build ID and pin, and show only whether pdf.js was on, but a
page or a tool reply that differs between the builds can still say which arm is which, so
`diagnoses.json` records that caveat too. A devtools-against-playwright run needs no
blinding, since the tool names give the arm away; its items carry `blinded: false`.

**Every claim cites a file.** A row's output (`schemas()` in `judge.mjs`, forced through
the SDK's `outputSchema`) holds a summary, a `primary_cause` and `contributing` causes
from a fixed list (`agent-capability`, `agent-shortcut`, `tool-defect`,
`tool-missing-info`, `tool-silent-noop`, `harness`, `validator-false-fail`,
`validator-false-pass`, `extractor`, `fixture`, `infra`, `none`), `grade_correct` and
`legitimate` (earned through the surface) with notes, a confidence, the wasted step
ranges, the trigger call (step, tool and a quote of its reply), the tool behaviours (tool,
behaviour, the turns and tokens it cost, evidence), and evidence items of `{file,
locator, quote}`. A pair's output gives each arm the same verdict, and adds the
`difference_driver` (surface, agent variance, draw, grading, harness, none), the better
arm and the surface differences, each with the turns and tokens it moved. A question's
output is an answer and its cited findings, a standing question's its fixed fields
(below). The evidence gate re-reads each cited file,
normalised as the extractor's quote gate normalises (JSON escapes undone), a
pretty-printed JSON file also as the one line `jq -c` prints; an unblinded question's
`run/tool-calls/...` citation reads the run directory, since its staged `run/` holds
`results.json` alone. It nulls a
quote the file does not hold, one that only a step header holds, and an elided quote
unless one part runs 20 characters and the parts sit within 400 characters of each
other; it moves a quote cited at the wrong step or line to where it is and logs the move.
It nulls a trigger that is not that arm's call or whose tool or reply quote is not that
call's (`firefox/<tool>` and `mcp__firefox__<tool>` both name `<tool>`), and drops a
wasted range outside the arm's steps. Each kept quote records where it sits (`from`), and
each claim needs a quote of the right kind:

| claim | needs a kept quote of |
|---|---|
| a `tool-*` cause | that arm's replies or errors (steps file, tap log, rollout) or the tool's source |
| a `validator-*` cause, a disputed grade | the validator (`eval/tasks`, `answers.mjs`, `extract.mjs`), the arm's state or `results.json` |
| a tool behaviour | its own arm's calls, replies, tap log, rollout or state, or the tool's source |
| a pair's surface difference | each arm's own files |
| a `surface` driver | a supported surface difference |
| a question's finding, a `tokens` sink, a `blinding` tell, a `gap` mechanism of another kind | any kept quote |
| a `gap` mechanism of a `tool-*` kind | some arm's calls, replies, tap log, rollout or state, or the tool's source |
| a `failures` pattern, whose cause is a `tool-*` | the replies or errors of each arm its rows name, or the tool's source |
| the newer arm `--ask blinding` names | a supported tell that points to it |

A claim without one is marked `unsupported`, a pair without a verdict on one arm records
it in `missing_arms`, and a quote from a file the judge wrote under `scratch/` supports
nothing. A disputed grade sets `legitimate` false, as the prompt defines it. A row that
`--ask failures` names must be one of the question's failed rows, under the table's name
or its staged condition's; any other is dropped and logged. `rule-checks.mjs` checks, in
the free gate, the gate, the blinding, the format rewrites on every staged file of a
synthetic two-build run, their caveats, the source and output denies, and the standing
questions' totals (against `abReport` on the same rows), gate and printed commands.

**Standing questions.** `--ask <preset>` asks one of the owner's standing questions over
the arms `--ab` names, each a fixed question with a fixed schema (`ASK_PRESETS` in
`judge.mjs`), so answers compare across runs:

| preset | asks | lists |
|---|---|---|
| `gap` | what mechanism explains the overall cost gap between two arms, each quantified per arm, its share of the gap and whether it is broad or a few tasks' | `mechanisms`, and what is `unexplained` |
| `tokens` | what produced each sink of two arms' input and output tokens, starting from the token ledger's split, which the A/B report's "Where the tokens go" prints free | `sinks` |
| `failures` | what the tool-attributable failures have in common, grouped by tool behaviour, and the failures no tool explains | `patterns`, `not_tool` |
| `blinding` | whether the files say which of two builds is newer, and every tell | `tells`, `newer_arm` |

Each prompt carries the per-arm totals the eval computed over the paired rows. For two
arms they are the A/B report's own figures, computed by its functions (`ab.mjs`
`pairedSums` and `passPairs`), so the passes and the output, total input, turns and cost
sums are the report's: on the codex A/A sweep's @old against @new, 96 against 98 passes
over 101 pairs, 89810 against 103474 output tokens and $5.6807 against $7.4534, as in
its A/B report. The table adds tool reply and snapshot characters, script calls, page
text reads, stale uids, codex requests, exec cells, discovery cells and outputs the
harness cut, and how many pairs each arm spent more on; its last column is a ratio of
sums, where the A/B report leads with the geometric mean of the per-task ratios (1.216
against the table's 1.296 for the Haiku sweep's total input). `diagnoses.md` prints the
table above the answer, so a number the judge quotes can be checked against the eval's
own. `tokens` also carries the token ledger's split of each arm's tokens, the figures
"Where the tokens go" prints, since the ledger measures where the tokens go and the
question asks what produced them. The judge is told to take those sums as given and
quantify what explains them, and `gap` tells it that extra turns and input are what a
gap is made of, not a mechanism, defines each kind of mechanism (a tool one arm lacks is
`tool-capability`, not `agent-route`; a cut the tool makes is `tool-replies`, one codex
makes `harness`) and asks that no event count under two mechanisms. `ab.mjs` on a
blinded staged run bootstraps with a placeholder seed, so its intervals differ slightly
from the run's own report (turns [0.749, 0.842] against [0.751, 0.842] on the codex @old
against @new), and the prompt says so. `blinding` needs two builds of one tool, and
`gap` and `tokens` two arms. A preset's output goes to
`<run-dir>/diagnoses-<preset>--<A>--<B>.json` unless `--out` names another. `run.mjs
--report-from` prints the command of each preset the run can answer: `gap` and `tokens`
over the arms its `--ab` names, or the run's two conditions in the order
`meta.conditions` lists them; `failures` over every condition unless `--ab` names two;
`blinding` only over two builds; a run of one condition gets `failures` alone.

Measured on 2026-09-21, one call each. `gap` on the codex A/A sweep's @old against @new
($0.17) named four mechanisms, each broad (@new cost more on 93 of 101 pairs): the larger
catalog with the server instructions only @new sends, printed again in 259 discovery
cells against 105 (about 30% of the cost gap); @new's `get_page_text`, which @old lacks
(168 reads against none, about 10%); outputs the harness cut (101 against 1, about 8%);
and the agents' longer route (about 42%, what it could not tie to a tool). It ruled out
reply volume, of which @old's replies carry more. Its prose counted 263 discovery cells
and 172 page reads, over every row rather than the 101 pairs the table sums. That is the
catalog cut "Codex drives the browser from scripts" describes, which the
instructions-off run (`run-2026-09-21T22-50-33-204Z`) measured. Earlier prompts did
worse: one without the kinds' definitions or the rule against counting an event twice put
discovery at 45% and harness cuts at 20%, the same catalog prints under both, and called
the route `agent-route` "with the same available browser capabilities" though @old lacks
`get_page_text` ($0.23); one without the sentence on turns named the turns themselves as
the mechanism, with no quote ($0.18). `gap` on the Haiku A/A sweep's @new against
playwright-mcp ($0.15) named the larger catalog (about 30%), the longer route (50%),
firefox-devtools-mcp's cut snapshots (10%, as `tool-replies`) and `get_page_text` (5%),
and ruled out reply volume. The gate kept 5 of its 14 quotes: 7 were sums it computed,
such as `"turns":1983`, which no file holds, and 2 were step headers alone, so its
`get_page_text` mechanism is unsupported. Its run on the earlier prompt ($0.13) labelled
the snapshot cut `harness`. `tokens` ($0.15) and `failures` ($0.28) on the codex @old
against @new, on the earlier prompt and staging, answered in their schemas; `failures`
put mfa-login's cut welcome line in both arms and the missing response body of
mid-flight-rate in @old alone. Gated again today, the mfa-login pattern is unsupported:
its quotes print uids as that staging numbered them. Each answer's numbers beyond the
totals are the judge's arithmetic: `tokens` put @new's "all other browser tools" at
290,886 reply characters, where the table's total less the sinks it listed leaves 28,886.
Its prompt now carries the token ledger's split, and no paid call has run on it yet.

**Output.** `<run-dir>/diagnoses.json` (or `--out`) holds every item with its gated
output, the model's raw output, the gate's log, the tokens, requests and cost of its call
and its isolation problems, the codex CLI and SDK versions and tool mode, and the
installed firefox-devtools-mcp with whether the judge could read its source
(`devtools_source`); each call's rollout is kept beside it. `diagnoses.md` groups the items by primary cause and by tool
behaviour with per-arm counts, lists the disputed grades and the outcomes the surface did
not earn, prints each pair's comparison and each answer, and ends with every call's
spend, cache writes included. Above an unblinded run's counts it says the judge knew
which tool each arm drove; above a blinded run's it lists the format rewrites and the
blinding caveats. An output of questions alone prints no cause or behaviour tables.
It never writes `success` or any metric. Its quotes of the state files carry graded
values, so, as with `states/`, `bundle.mjs` ships neither. `--canned <diagnoses.json>`
gates an earlier output again with today's gate and staging, with no call, under the
letters that output drew. A quote that prints a uid as an earlier staging numbered it,
or cites a source today's rules shut, is nulled.

HTML reports can include the judge's per-arm verdicts, tool findings, and cited evidence
when given `--diagnoses`. Reports beside a run link to its graded transcripts and rollouts;
the curated site copies them only for entries with `"traces": true`. The site's optional
`"video"` path copies an MP4 beside the home page and plays it muted on load unless
the viewer prefers reduced motion. These
files and judge evidence may contain task answers and local paths, so review the
generated site before publishing it. Server state files are never copied.

runs (`run-2026-09-20T22-45-29-568Z`, `run-2026-09-20T22-52-41-101Z`). Those reviewers read

The validation figures are in-sample. The changes of passes 2 to 4 answered
disagreements on validation rows (the rows' browser fields for pdf-bill, "none" at two
wasted calls for session-expiry, deliberate decoys for password-reset), and the dev set
ran only on the pass 1 and pass 2 prompts (10 of 11 and 9 of 10 by family), so no pass was
scored on a frozen prompt. The heldout set is the one out-of-sample figure, and it is
small: the shipped prompt agrees with the reviews on 7 of 11 causes, one more than the
baseline, and the interval covers both the validation figure and the baseline. Out of
sample, the judge's primary cause has not been shown to beat reading it off the grade.
Its legitimacy verdicts sit close to that baseline too, since the reviews call nearly
every outcome earned. The budget ran out before the twelfth heldout row
(`playwright-mcp|hovercard-oncall` of the codex sweep).

An interval at 54 rows spans about 12 points each way, so passes 3 and 4 do not differ
measurably, and run-to-run variance at a fixed prompt was never measured. Pass 4's
sentence was kept because it removed pass 3's one dispute of a right grade; its 4-point
drop in cause agreement is two rows. The heldout prompt added to pass 4 only the evidence
rules the gate enforces. Gating pass 4's and the pairs' stored outputs again with the gate
of that time (`--regate`) changed no cause, set `legitimate` false on the one disputed
grade that had it true, and marked 8 of the 17 pair surface differences unsupported. All
of this predates the source rule (`sourceShutFor`), which now shuts the installed 0.10.3
source to the judge of these four runs on 0.9.15, and says so in the prompt, so the
shipped prompt for them is not the one scored, and a re-gate now nulls any quote of that
source, which may turn a `tool-*` cause unsupported. The stored validation outputs sit in
no stored run, and no set has been judged or re-gated since.

Wrong grades were found by signals, not by reading. The judge found 5 of the 6 grades the
reviews called wrong, and a deterministic signal carried each of the five. For the three
false fails (phish-pick, popup-storm, feed-needle), `regrade.mjs` under today's
validators, fixed after the reviews, flips the stored FAIL to PASS, and every grade note
cites it. The two false passes it found (body-only-ref, hovercard-oncall) carry the row's
`shell_assisted` flag, which the prompt names. The one wrong grade that needed judgement,
Haiku's ledger-sum, whose total the shell computed from pages the browser also showed and
which has no `shell_assisted` flag, was missed in passes 3 and 4: the judge called it a
shortcut with a correct grade. Finding a wrong grade by reading alone is unmeasured, at 0
of 1.

On the A/A control the judge named no `surface` driver in 6 pairs (95% CI 0-39%): it named
agent variance for five, the three whose arms split pass and fail among them, and a draw
for one. It
named one surface difference, and the gate kept it: in the Haiku playwright-mcp
range-select pair, one arm's final snapshot came back as a file link and the other's
inline, which the judge credited to the tool, though the arm that got the link had asked
for a file. It named a better arm in all six. Six pairs bound the false-attribution rate
only loosely.

Four caveats bound these numbers. Each review is one agent's labels, checked by a
synthesis, so there is no labeller-to-labeller ceiling to read them against. The
repository the judge reads documents some of what the reviews found (code comments, docs
and the README's other sections name body-only-ref, hovercard-oncall, popup-storm and
others), which helps the judge on those rows as it would on any row with a known defect.
And until `judge.mjs` left `judge-reference.json` and `judge-validate.mjs` out of the
judge's copy of the repository, 11 of the 216 validation items above searched the
repository for a task id and printed their own reference labels; the scorer finds such an
item in its rollout (a reference row, this file's mapping or a scored agreement file) and
leaves it out, which is why passes 1 and 2 score fewer than 54, and pass 4's five were
judged again after the fix. And the four runs ran firefox-devtools-mcp 0.9.15 as the
dependency, which is 0.10.3 in this checkout since b8233a9. The passes above predate
`devtools_source`, which records the installed build and whether the judge could read
it, so which build's source they read as the tool's is unknown; a set judged again now
reads none.

**What it may be used for.** A diagnosis is a lead with its evidence attached: read the
cited quotes before acting on it. Use it to find the rows worth reading, to name tool
behaviours and their cost for a developer to reproduce with a probe or spike, and to find
shell-assisted or otherwise unearned outcomes. A pair's supported `surface_differences`
and a question's findings are leads of the same kind. A disputed grade is a lead to check
with `regrade.mjs`; the judge has not shown that it finds a wrong grade that neither a
regrade nor `shell_assisted` flags. A standing question's answer is a lead to the
mechanism behind a gap the A/B report measured: pair mode missed the codex 0.10.3 gap,
spread evenly over the tasks, where `--ask gap` found it. Check its numbers against the
totals it printed, and prove the mechanism with a probe, a spike or an ablation run, as
the instructions-off run proved that one.

**What it may not be used for.** No count of diagnoses is a measurement: a cause
distribution, a per-arm tally or a tool-behaviour total is not a result to quote, and it
never replaces triage, the A/B report or a regrade; out of sample, the judge's cause has
not beaten the grade-only baseline. A standing question's shares and amounts beyond the
eval's totals are the judge's estimates, and each answer is one sample: its variance at a
fixed prompt has not been measured. Pair mode's per-arm causes agree with the reviews less
than row mode's, so take a row's cause from rows mode. Before reading a build-vs-build
comparison, run pair mode on the same run's A/A pair: `--mode pairs --ab
firefox-devtools-mcp@base,firefox-devtools-mcp@aa` judges the pairs with a failure or a
1.5x output gap, the population the A/A control measured, and `--all` adds the rest. Every
`surface` driver or supported surface difference there is noise. Rerun `--set heldout` and
`--set aa` (about $1.50) on every change to the prompt, the schema or the model, and read a
drop beyond the interval as a regression; `--set validation` measures a prompt on the rows
it was tuned on.

## Layout

For run setup and build pins, see `eval/running.md`; for A/B reports, the ship
rule and triage, see `eval/analysis.md`. Judge guidance stays here because the
judge's staged repository excludes this section to keep its reference answers out
of view.

| Path | What |
|---|---|
| `verify.mjs`, `verify-drivers/` | The free gate: 99 deterministic golden paths. `verify-extract.mjs` grades, logs and totals the paid `--extract` cases. |
| `run.mjs`, `backends/` | The paid runner (Claude Agent SDK, codex), and the free `scripted` backend, which answers each task from its golden-path driver. |
| `tasks/` | Task definitions — ask, `answerSchema`, `validate`. The web suite splits across `tasks/web/`, one module per family. |
| `answers.mjs` | The answer key. Excluded from result bundles and from the container image. |
| `extract.mjs` | Structured answer extraction and the shared comparators. |
| `mcp-stdio.mjs` | Stdio MCP client; resolves the tool server and the Firefox it launches per the orders above. |
| `mcp-tap.mjs` | The passthrough every condition's server runs behind, logging each call's latency and sizes to `tool-calls/*.jsonl`; `--no-tap` drops it. |
| `report.mjs`, `ab.mjs` | report.md, and the paired A/B report with its statistics. |
| `scripts/` | Readers of a finished run: `run-health.mjs`, `transcript.mjs`, `bundle.mjs`, `triage.mjs`, `tool-stats.mjs`, `token-ledger.mjs`, `regrade.mjs`, `compare.mjs`, `history.mjs`, and the opt-in `judge.mjs` with `judge-validate.mjs` and its `judge-reference.json`. They share `events.mjs`, `identity.mjs`, `state-file.mjs` and `row-evidence.mjs`. `row-evidence.mjs` reads the state a stored row was graded on from its state file (`rowState`), a row's shell assistance from the row, or from that state for a row older than `shell_assisted` (`shellAssistedOf`), and a codex row's `code_mode` and turns from its rollout (`withRolloutFacts`). `rule-checks.mjs` checks the reporting rules that read a row without a browser (reach's matching, the copied-cut rule, script recovery, shell assistance, whole-path labels, the firefox-devtools-mcp 0.10 reply formats, the judge's evidence gate, blinding, staging, format normalisation, denies and standing questions, the token ledger's sums, intervals and shares, and the browser a condition ran on) on the cases that made them and the cases they must not catch, the `--extract` bookkeeping against a stub extractor, and `run-health.mjs` on a consistent run and on each setup defect seeded into one. `token-ledger.mjs` splits each row's tokens by what they paid for ("Where the tokens go"). `stats-checks.mjs` checks `ab.mjs`'s statistics against exact tails, the figures a report prints against its helpers, the ratios `ab.mjs`, `compare.mjs` and `report.mjs` print against a reshuffle of their rows and a swap of their arms, and the interval, sign test and MDE against seeded simulations of the A/A noise `stats-aa.json` holds from the stored A/A sweeps (`--refresh` reads it again from them, `--repeats <run-dir>` prints a run's repeat SDs).
