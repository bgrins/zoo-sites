What we build

Kettleforge hosts source repositories for engineering teams that want review and build in one place and would rather not assemble them from four vendors. A repository on Kettleforge carries its issues, its pull requests, its Anvil pipelines and its package registry entries under the same permissions model, so a reviewer who can read the diff can read the job log that failed on it without asking anyone for a second account.

We started in 2017 with a single product decision that we have not revisited: review is the part of the workflow worth being slow and exact about. Everything else on the platform serves it. Pipelines exist so a reviewer knows whether the branch builds. The registry exists so the artefact a pipeline produced can be traced back to the commit that produced it. When those two disagree, we would rather block a merge than guess.

How review works here

A pull request on Kettleforge is a conversation with a gate on it. Line comments are staged rather than published one at a time, so an author is not paged six times while a reviewer reads down a diff; the reviewer submits them together with a summary and a verdict, and the author sees one coherent piece of feedback. A repository can require a verdict from a code owner, a passing set of required jobs, or both, and Forge merge stays blocked until the requirements the repository declared are actually met.

Branch protection, required jobs and code owners are configured per repository and are visible to everyone who can read it. We do not offer a way to override a gate quietly. An administrator can lift a requirement, and lifting it is recorded in the repository audit log with the account that did it and the reason they gave.
